# Домашнее задание к занятию «Микросервисы: подходы»

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.


## Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. 
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

Обоснуйте свой выбор.


**Сравнительная таблица программных решений:**

| Решение | Облачная система | Git и репозиторий на сервис | Триггеры (события/кнопка) | Шаблоны и параметры | Секреты и свои агенты | Параллельные сборки/тесты |
|---------|------------------|-----------------------------|---------------------------|---------------------|-----------------------|---------------------------|
| **GitLab CI** | Да (GitLab.com или облачный SaaS) | Да (нативная интеграция) | Да (`rules`, `when: manual`) | Да (`extends`, `variables`) | Да (CI/CD Variables, GitLab Runner) | Да (ключевое слово `parallel`) |
| **GitHub Actions** | Да (GitHub.com) | Да (нативная интеграция) | Да (`on:`, `workflow_dispatch`) | Да (`reusable workflows`, `inputs`) | Да (Secrets, Self-hosted runners) | Да (matrix strategy) |
| **TeamCity** | Да (TeamCity Cloud) | Да (поддержка любого Git) | Да (VCS Trigger, Run Custom Build) | Да (Templates, Configuration parameters) | Да (Secrets, собственные Build Agents) | Да (параллельные шаги и сборки) |

**Выбор решения:** **GitLab CI** (или **GitHub Actions**, если код уже размещен там).

**Обоснование выбора:**
GitLab CI идеально закрывает все требования как единая платформа:
1. **Облачность и Git:** Нативная поддержка, не требует сложных интеграций.
2. **Гибкость сборок:** Поддерживает шаблоны (`extends`), параметры (`variables`) и ручные запуски с параметрами (`when: manual`).
3. **Безопасность:** Встроенное хранилище секретов (CI/CD Variables с флагами Masked/Protected).
4. **Инфраструктура:** Позволяет легко подключать собственных агентов (GitLab Runner) на своих серверах и использовать кастомные Docker-образы для этапов сборки.
5. **Параллелизм:** Нативная поддержка параллельного выполнения задач и дробления тестов.

## Задача 2: Логи

Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
- минимальные требования к приложениям, сбор логов из stdout;
- гарантированная доставка логов до центрального хранилища;
- обеспечение поиска и фильтрации по записям логов;
- обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
- возможность дать ссылку на сохранённый поиск по записям логов.

Обоснуйте свой выбор.

**Сравнительная таблица программных решений:**

| Решение | Сбор из stdout | Гарантированная доставка | Поиск и фильтрация | UI и ссылки на поиск | Сложность эксплуатации |
|---------|----------------|--------------------------|--------------------|----------------------|------------------------|
| **Vector + Elasticsearch + Kibana** | Да (через Docker log driver или file) | Да (буферизация на диске в Vector) | Отличная (полнотекстовый поиск ES) | Да (Kibana, сохраненные view) | Средняя |
| **Loki + Promtail + Grafana** | Да (Promtail читает stdout) | Да (retry механизм) | Хорошая (по меткам и времени) | Да (Grafana Explore, shareable links) | Низкая (легче, чем ES) |
| **Fluentd + Elasticsearch + Kibana** | Да | Да (буферизация) | Отличная | Да | Высокая (сложный конфиг Fluentd) |

**Выбор решения:** **Vector + Elasticsearch + Kibana**

**Обоснование выбора:**
1. **Гарантированная доставка:** Vector использует надежную буферизацию на диске, что предотвращает потерю логов при временной недоступности хранилища.
2. **Минимальные требования:** Vector легко настраивается на чтение `stdout` контейнеров (через source `docker_logs`).
3. **Поиск и UI:** Elasticsearch обеспечивает молниеносный полнотекстовый поиск, а Kibana предоставляет мощный интерфейс для разработчиков с возможностью сохранения и шеринга ссылок на конкретные поисковые запросы.

## Задача 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.

**Сравнительная таблица программных решений:**

| Решение | Метрики хостов | Метрики сервисов (контейнеров) | Специфичные метрики сервисов | Язык запросов и агрегация | Визуализация (Dashboard) |
|---------|----------------|--------------------------------|------------------------------|---------------------------|--------------------------|
| **Prometheus + Grafana** | Да (через Node Exporter) | Да (через cAdvisor или сам Prometheus) | Да (через endpoint `/metrics`) | Отличная (PromQL) | Отличная (Grafana) |
| **Zabbix** | Да (агент) | Да (через шаблоны Docker) | Да (через UserParameters) | Хорошая (свой язык) | Встроенная, но менее гибкая |
| **Datadog** | Да (агент) | Да | Да | Отличная | Отличная (но платная) |

**Выбор решения:** **Prometheus + Grafana + Node Exporter + cAdvisor**

**Обоснование выбора:**
1. **Универсальность:** Node Exporter собирает метрики хоста (CPU, RAM, Disk, Network), а cAdvisor автоматически снимает метрики потребления ресурсов каждым контейнером.
2. **Специфичные метрики:** Сервисы сами отдают метрики по эндпоинту `/metrics` (формат Prometheus), что является индустриальным стандартом.
3. **Визуализация:** Grafana предоставляет лучший на рынке UI для создания кастомных дашбордов, агрегации данных и настройки алертов.
